# Generate Verified Python Tests With Zero API Keys — How Quell's Rule Engine Works

Every AI-powered test generation tool has the same pitch: give it your code, get back tests. What they don't tell you: your code is sent to a third-party API, the tests are generated by a model that doesn't know your requirements, and there's no guarantee the tests actually prove anything.

[Quell](https://quell.buildsbyshashank.tech) takes a different approach. Its primary test generation path is a **deterministic rule engine** — no LLM, no API key, no network call. For the vast majority of Python requirements, rules are faster, more reliable, and more privacy-preserving than language models.

## The Requirements That Rules Handle Well

Requirements fall into predictable patterns. When a docstring says "Raises ValueError if amount <= 0", there's exactly one meaningful test:

```python
with pytest.raises(ValueError):
    function(amount=0)
```

When a Pydantic model says `Field(gt=0, le=10_000)`, there are exactly two boundary tests:

```python
with pytest.raises(ValidationError):
    Model(amount=0)       # at lower boundary

with pytest.raises(ValidationError):
    Model(amount=10_001)  # at upper boundary
```

These patterns don't require intelligence. They require pattern matching. A rule handles them instantly, deterministically, and without sending your code anywhere.

## The Five Rule Types

Quell's rule engine handles five `ConstraintKind` values:

### MUST_RAISE

Triggered by `Raises:` entries in docstrings.

```python
# Raises:
#     ValueError: If amount is <= 0.
```

Generated test:
```python
def test_process_payment_must_raise_value_error():
    with pytest.raises(ValueError):
        process_payment(amount=0, currency="USD")
```

Violation injection: comment out the `raise ValueError` statement inside the function. If the test still passes after injection, it's discarded.

### BOUNDARY

Triggered by `Field(gt=N)`, `Field(lt=N)`, `Field(min_length=N)`, `Field(max_length=N)` in Pydantic models, or from Args: sections with explicit bounds.

```python
class Item(BaseModel):
    price: float = Field(gt=0, lt=1000)
```

Generated tests:
```python
def test_item_boundary_price_lower():
    with pytest.raises(ValidationError):
        Item(price=0)

def test_item_boundary_price_upper():
    with pytest.raises(ValidationError):
        Item(price=1000)
```

Violation injection: weaken the `Field` constraint (e.g., `Field(gt=-1)` instead of `Field(gt=0)`).

### ENUM_VALID

Triggered by `Literal["a", "b", "c"]` type annotations.

```python
def set_status(status: Literal["active", "inactive", "suspended"]) -> None:
```

Generated test:
```python
def test_set_status_enum_valid_status():
    with pytest.raises((ValueError, TypeError)):
        set_status(status="__invalid__")
```

### MUST_RETURN

Triggered by `Returns:` sections in docstrings.

```python
# Returns:
#     dict with keys: transaction_id, status.
```

Generated test:
```python
def test_process_payment_must_return():
    result = process_payment(amount=10.0, currency="USD")
    assert isinstance(result, dict)
    assert "transaction_id" in result
    assert "status" in result
```

### NOT_NULL / TYPE_CHECK

Triggered by PySpark `StructField` definitions with `nullable=False`.

```python
StructField("amount", DoubleType(), nullable=False)
```

Generated NOT_NULL test:
```python
def test_schema_not_null_amount(spark):
    with pytest.raises((AnalysisException, Exception)):
        spark.createDataFrame([Row(amount=None)], schema=schema).collect()
```

## How Signature Inspection Works

The hardest part of rule-based test generation is building a valid function call. If your function signature is:

```python
def process_payment(
    amount: float,
    currency: str,
    payment_method: PaymentMethod,
    idempotency_key: Optional[str] = None,
) -> dict:
```

The rule engine needs to construct a call with real arguments. Quell's `sig_inspector.py` module reads the function signature via AST and maps each parameter to a stub value:

| Type annotation | Stub value |
|----------------|-----------|
| `str` | `"test"` |
| `int` | `1` |
| `float` | `1.0` |
| `bool` | `True` |
| `Path` | Uses `tmp_path` fixture |
| `Optional[X]` | `None` |
| `List[X]` | `[]` |
| `Dict` | `{}` |
| `Callable` | `lambda: None` |
| `datetime.datetime` | `datetime.datetime(2024, 1, 1)` |
| Custom classes | Instantiated with default/stub args |

Name-based inference fills gaps: a parameter named `email` gets `"test@example.com"`, `url` gets `"https://example.com"`, `path` gets a `Path("test")`.

## The `--no-llm` Flag

Run Quell with no network calls:

```bash
quell check src/ --no-llm
quell check src/ --fix --no-llm
```

With `--no-llm`:
- The rule engine handles all supported ConstraintKinds
- Requirements that the rule engine can't handle are listed but skipped (not sent to LLM)
- After `--fix`, Quell prints: **"Your code never left your machine."**

This is the default behavior — `llm_provider` defaults to `"none"` unless you explicitly configure one.

## When LLM Is Actually Needed

The rule engine handles the predictable patterns. Some requirements don't fit:

```python
# Raises:
#     PaymentGatewayError: If the payment gateway is unreachable.
```

Generating a test for this requires knowing how to trigger a gateway failure — mocking `httpx`, setting up a fake server, or checking error conditions. This is context-dependent in ways that rules can't generalize.

For these cases, Quell falls back to an LLM — but only if you've configured one. Without configuration, these requirements are flagged as uncovered but not hallucinated into bad tests.

The heuristic: if the requirement has a clear violation condition that can be expressed purely from the type/value space, rules handle it. If it requires domain knowledge or external state, LLM handles it. Most requirements — in our measurement, around 75% — are in the first category.

## Comparing Rule-Based vs LLM-Generated Tests

| Property | Rule engine | LLM |
|----------|------------|-----|
| Speed | ~ms per test | 1-5s per test (API latency) |
| Cost | Free | API costs |
| Privacy | Zero code sent | Code sent to provider |
| Determinism | Yes — same input, same output | No |
| Correctness | High (verified by two-phase check) | High (also verified) |
| Coverage | ~75% of requirements | ~95% of requirements |
| Requires config | No | Yes (API key) |

For teams that want fast, free, private test generation — the rule engine covers most of what you need.

## Running It

```bash
pip install quelltest
quell check src/ --no-llm
```

The scan takes seconds. Requirements are extracted from docstrings and Pydantic models without executing your code. No API key, no sign-up, no configuration.

```bash
quell check src/ --fix --no-llm
```

For each uncovered requirement that the rule engine can handle, a test is generated, verified in two phases, and written to disk.

The diagnostic report at `.quell/report.json` shows exactly which requirements were handled by rules, which were skipped, and why — without including your source code.

## The Principle

Good tooling doesn't require you to trust a black box. The rule engine is deterministic: you can trace exactly why a test was generated, what violation was injected, and why it was accepted or rejected.

That's the kind of tool you can put in CI with confidence.
