# How It Works

Quell has five stages: **Read → Check → Generate → 5-Gate Pipeline → Route**. Each candidate test is routed to one of three buckets based on how many gates it passes.

## Overview

```
Spec readers (docstrings, Pydantic, PySpark)
        │
        ▼
  list[Requirement]
        │
        ▼
Coverage checker (AST scan — no test execution)
        │
        ▼
Test synthesizer
  Rule engine  → handles ~75% of requirements (no network)
  LLM engine   → fallback for complex cases (opt-in)
        │
        ▼
5-Gate Pipeline
  Gate 1: AST valid + imports resolve
  Gate 2: Originality (AST fingerprint + n-gram)
  Gate 3: Security (no forbidden operations)
  Gate 4: Passes on correct code
  Gate 5: Fails on violated code
        │
        ▼
Three-bucket routing
  WRITTEN    → passed all 5 gates → written to disk
  SCAFFOLDED → failed any gate   → stub written to tests/scaffold/
  FLAGGED    → cannot synthesize → reason shown, no file written
```

## Stage 1: Read specs

Quell reads specifications that already exist in your codebase. Each spec reader returns a list of `Requirement` objects and returns `[]` on any error — they never raise.

### Docstring reader

Parses Google-style and plain docstrings:

- `Raises:` blocks → `MUST_RAISE` requirements (multi-line conditions captured)
- `Returns:` blocks → `MUST_RETURN` requirements
- Boundary phrases ("must be greater than 0") → `BOUNDARY` requirements
- Enumeration phrases ("one of USD, EUR, GBP") → `ENUM_VALID` requirements

### Type reader

Reads Pydantic models and type annotations:

- `Field(gt=0)`, `Field(ge=18)`, `Field(min_length=1)` → `BOUNDARY` requirements
- `Literal["USD", "EUR", "GBP"]` fields → `ENUM_VALID` requirements

### Bug reader

Converts natural language bug descriptions into `BUG_REPRO` requirements using an LLM prompt. Used by `quell reproduce`.

## Stage 2: Check coverage

An AST-based coverage checker scans your test files and marks each `Requirement` as covered or uncovered. No test execution required.

| Requirement kind | Covered if test file contains... |
|-----------------|----------------------------------|
| `MUST_RAISE` | `pytest.raises(ExceptionType)` |
| `BOUNDARY` | assertion with boundary constants |
| `ENUM_VALID` | assertion referencing the enum values |
| `MUST_RETURN` | assertion on the return value |

When in doubt, the checker marks a requirement as uncovered. Duplicate tests are cheaper than missed gaps.

## Stage 3: Test synthesis

For each uncovered requirement, Quell generates a candidate test:

- **Rule engine** — deterministic, no LLM, no network. Handles `MUST_RAISE`, `BOUNDARY`, `ENUM_VALID`, `NOT_NULL`, `TYPE_CHECK`, `MUST_RETURN`.
- **LLM engine** — fallback for complex or unstructured cases. Only called when rule engine returns `None` and `--use-llm` is set.

## Stage 4: The 5-gate pipeline

Each candidate test passes 5 gates. Failure at any gate routes the requirement to SCAFFOLDED (not rejected — a stub is written so you can complete it).

### Gate 1 — AST validity

The generated test is parsed as Python source. Import references are checked to resolve. A test that can't parse or can't import the target function is useless as a WRITTEN test.

### Gate 2 — Originality

An AST fingerprint and n-gram comparison ensure the generated test doesn't duplicate an existing test. This prevents Quell from writing a test that's already covered.

### Gate 3 — Security

The generated test is scanned for forbidden operations: no `os.system`, no `subprocess.Popen` with shell, no file deletion, no credential reads. A test that does dangerous things is rejected at this gate.

### Gate 4 — Passes on correct code

The test runs in a subprocess against the **original, unmodified source**. If it fails here, the generated test is logically wrong — it doesn't match the requirement's success condition.

```python
# Gate 4: must pass
pytest temp_test.py            # ← against original source
```

### Gate 5 — Fails on violated code

Quell injects a minimal violation into the source and runs the test again. If the test still passes after the violation, it doesn't actually catch the bug.

```python
# Gate 5: must fail
inject_violation(source)       # ← comment out raise, weaken bound, etc.
pytest temp_test.py            # ← test must fail
restore_source()               # ← always restored in finally block
```

Violation injection per constraint kind:

| Kind | Violation |
|------|-----------|
| `MUST_RAISE` | Comment out the `raise` statement |
| `BOUNDARY` | Weaken the threshold to `-9999` |
| `MUST_RETURN` | Replace the return with `return None` |
| `NOT_NULL` | Remove the null check |
| `ENUM_VALID` | Remove the enum validation guard |

## Stage 5: Three-bucket routing

After the pipeline, each requirement lands in one bucket:

| Bucket | Condition | Output |
|--------|-----------|--------|
| WRITTEN | Passed all 5 gates | Injected into test file via libcst |
| SCAFFOLDED | Failed any gate (or no test generated) | Stub written to `tests/scaffold/` |
| FLAGGED | Cannot synthesize at all | Reason printed, nothing written |

### WRITTEN — libcst injection

Verified tests are injected into the target test file using **libcst** — a lossless concrete syntax tree parser. This preserves your comments, blank lines, and indentation. The file is backed up before write and restored on failure.

### SCAFFOLDED — stub files

When a test can't pass all gates, Quell writes a stub so you don't lose the edge case:

```python
# quell: scaffold — complete the assertions below and move to your test suite
def test_quell_scaffold_pay_req_abc123():
    """
    Quell scaffold — gates passed: 2/5
    Constraint: raises ValueError when amount <= 0
    """
    from payments import pay
    # quell: complete assertion
    # TODO: call pay() and assert the edge case behaviour
    pass
```

The scaffold dir (`tests/scaffold/`) is auto-added to `.gitignore` by `quell init`. Move completed stubs to your main test suite.

### FLAGGED — with reasons

FLAGGED items always show a one-line reason:

```
✗ FLAGGED  src/billing.py:142  depends on external API — no violation injectable
✗ FLAGGED  src/user.py:87     guard checks self.attr — needs class instantiation
```

## Production Readiness Score (PRS)

PRS is a 0–100 score computed after every `quell find` run:

```
PRS = (Σ confidence_of_WRITTEN_tests / (total_edge_cases × 100)) × 100
```

**Modifiers:**
- **+5** if all FLAGGED items are documented with `# quell: flagged`
- **-10** if any HIGH-confidence test is disabled with `@pytest.mark.skip`

**Tiers:**

| Score | Tier | Emoji |
|-------|------|-------|
| ≥80 | Production Ready | 🟢 |
| ≥60 | Review Needed | 🟡 |
| <60 | Needs Work | 🔴 |

PRS is written to `quell-report.json` and shown by `quell score`. The GitHub Action posts it as a PR comment on every scan.

## Design invariants

These invariants are enforced throughout the codebase:

1. **Verifier** — always restores source files in a `finally` block
2. **Writer** — always backs up before writing, always restores on failure
3. **Writer** — always validates CST parses correctly before writing
4. **No code leaves your machine** unless an LLM provider is explicitly configured
5. **LLM is only called** when the rule engine returns `None` and `--use-llm` is set
6. **Verification runs in a subprocess** — never in-process (module cache)
7. **Every spec reader returns `[]` on error** — never raises
