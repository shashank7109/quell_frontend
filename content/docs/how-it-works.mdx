# How It Works

Quell has four stages: **Scan → Generate → Verify → Write**. Each stage is independent, reversible, and safe by default.

## Stage 1: Scan

Quell reads your mutation testing tool's output and extracts survived mutants.

For **mutmut**, it opens `.mutmut-cache` (a SQLite database) directly. It auto-detects whether you're on mutmut 2.x or 3.x by checking the database schema.

For **Stryker**, it reads `reports/mutation/mutation.json` and extracts all mutants with status `Survived`.

Each mutant is represented as a `SurvivedMutant` object containing:
- The file path and line number
- The original code and the mutated code (as a unified diff)
- The enclosing function's source (extracted via `ast.parse`)
- Existing test names in the corresponding test file

## Stage 2: Generate

Quell classifies each mutant by its mutation operator, then runs the appropriate generator.

### Rule-based generation (no LLM)

For 9 common operators, Quell generates tests deterministically:

| Operator | Generation strategy |
|----------|---------------------|
| `BOUNDARY_SHIFT` | Test at exact boundary value (e.g., `amount=0` for `> 0` → `>= 0`) |
| `ARITHMETIC_SWAP` | Use non-zero, non-symmetric inputs (`x=3, y=2` distinguishes `+` from `-`) |
| `COMPARISON_FLIP` | Provide an input where the original comparison is `True` |
| `CONSTANT_MUTATION` | Assert the exact constant value, not a range |
| `RETURN_MUTATION` | Assert the exact return value, not `None` |
| `LOGICAL_SWAP` | Provide input where exactly one condition is true |
| `CONDITION_NEGATE` | Input that makes the original condition true |
| `STATEMENT_REMOVAL` | Assert the side effect of the removed statement |
| `STRING_MUTATION` | Assert the exact non-empty string value |

Rule-based tests are generated in microseconds. No API key, no internet, no latency.

### LLM fallback (only for UNKNOWN)

If the operator is `UNKNOWN`, Quell calls your configured LLM provider with a structured prompt containing:
- The full function source
- The exact diff (original → mutated)
- Existing test patterns in the file
- Clear instructions to write a minimal, deterministic test

LLM is never called for operators the rule engine handles.

## Stage 3: Verify

This is the most important stage. A test is only accepted if it passes both conditions:

1. **Original suite passes** — run `pytest <temp_test_file>` against the original source. If this fails, the generated test is already broken.
2. **Mutant is killed** — apply the mutation, run `pytest <temp_test_file>` again. If the test still passes, it doesn't actually kill the mutant.

Both conditions are required. A test that passes on original but passes on mutant too is an equivalent-mutant candidate and is skipped.

### Isolation

Verification always runs in a subprocess (`subprocess.run`), never in-process. This ensures:
- Mutations load fresh (no module caching)
- Failures are isolated (a crashing test doesn't kill Quell)
- Timeouts are enforced cleanly

### File safety

```
try:
    backup_source()
    apply_mutant()
    run_pytest()
finally:
    restore_source()    # ALWAYS runs
    cleanup_temp()      # ALWAYS runs
```

The source file is **always** restored, even if verification crashes or times out.

## Stage 4: Write

Verified tests are injected into the target test file using **libcst** — a lossless concrete syntax tree parser.

Unlike regex-based injection, libcst:
- Preserves your existing comments, blank lines, and indentation
- Validates the resulting source parses correctly before writing
- Backs up the file before making any change
- Restores on failure

The final write sequence:

1. Parse existing test file with libcst
2. Parse new test function with libcst
3. Append the new function node
4. Validate the combined source
5. Write to disk

If step 4 or 5 fails, the backup is restored and Quell exits cleanly.

## Audit log

Every action Quell takes is appended to `.quell/audit.jsonl` as a structured JSON record:

```json
{
  "timestamp": "2026-05-08T14:32:01Z",
  "mutant_id": "14",
  "action": "test_written",
  "file_path": "tests/test_calculator.py",
  "test_function_name": "test_kill_mutant_14",
  "verification_status": "verified"
}
```

Run `quell report` to view the audit log in a formatted table.

## Design invariants

These invariants are enforced throughout the codebase and must never be broken:

1. **`verifier.py`** — always restores source files in a `finally` block
2. **`writer.py`** — always backs up before writing, always restores on failure
3. **`writer.py`** — always validates CST parses correctly before writing to disk
4. **No code is sent to any server** unless an LLM provider is configured
5. **LLM is only called** for `UNKNOWN` operators — never for ones the rule engine handles
6. **Verification runs in a subprocess** — never in-process
